# UI reference and dashboard design research for the IELTS Academic simulator

Date: 2026-10-26. Stack: React + Tailwind + shadcn/ui, TypeScript, frontend only.

Status: complete (Part A and Part B written; verdict at the end).

## Part A: the four 21st.dev references

Method: each 21st.dev page was opened in the browser pane (the pages are client-rendered), the demo "Usage.tsx" was read, the compiled preview bundle on cdn.21st.dev was downloaded and grepped for implementation markers (useEffect, createElementNS, shadcn tokens, `dark:` variants, hex colours, reduced-motion handling), and the swapy component's full source was read from the UI Layouts shadcn registry JSON. Note: 21st.dev only shows the demo code; the component source itself is behind a free account and installs via `npx shadcn@latest add "https://21st.dev/r/<author>/<slug>?api_key=..."`.

### A1. Roman Vasnev, Finance Bento

- Page: https://21st.dev/@romanvasnev/components/finance-bento (preview bundle: https://cdn.21st.dev/romanvasnev/finance-bento/default/bundle.1792655549506-cff3770d-13a1-4e1c-9bc0-a9e0fd893d87.html). MIT. Published 22 Oct 2026. Category: Dashboards.
- Visual pattern: full-bleed black page, Geist + Geist Mono loaded from Google Fonts in a `useFonts()` effect, a 12-column bento (`grid-template-columns:repeat(12,minmax(0,1fr))` set as an inline style), one large hero card with a blue-to-violet gradient and a 5x7 dot-matrix number (`grid-template-columns:repeat(5,3px)` glyph cells that animate), a mirrored "net worth stream" area chart with hover tooltips, a semicircle allocation gauge, KPI tiles (one in acid lime `#E8FF1F`), mirrored cash-flow bars, crypto OHLC sparklines, weekly stock bars. Segmented period control (1M/3M/1Y/All) and a currency toggle (USD/EUR) in the header.
- Dependencies: none beyond React and Tailwind ("No chart library"). Charts are SVG built imperatively: the bundle contains a `createElementNS("http://www.w3.org/2000/svg", ...)` helper (`el(tag, attrs, parent)`), `requestAnimationFrame` loops and a `ResizeObserver`, all driven from `useEffect`. 11 `useEffect` calls in the bundle. It does read `matchMedia("(prefers-reduced-motion: reduce)")` once and stores it in a module constant.
- Theme: fixed dark. Zero occurrences of `bg-card`, `text-foreground` or `dark:` in the bundle; colours are hard-coded hex (`#E8FF1F`, `#A9B2FF`, `#FFB37A`, `#FFD0E6`, `#0b0b0c`, `rgba(255,255,255,.56)` etc.). It does not read shadcn tokens, so a light theme means forking the component.
- Good for: a marketing hero or a "wow" landing visual; a single brand-dark overview page where you control the palette.
- Mapping to an exam platform: hero card = predicted overall band (dot-matrix 6.5) with a band-history stream for Listening/Reading/Writing/Speaking; gauge = target-band readiness (e.g. "72% to 7.0"); lime KPI = best recent mock; mirrored cash-flow = correct vs incorrect per question type; sparklines = per-skill trend over the last 7 mocks; payments list = upcoming scheduled mocks; goals = target band per skill with progress.
- Trade-offs: the numbers and charts are not data-bound React; they are DOM mutations inside effects, so wiring real data later means re-running effects on every prop change, hand-writing scales, axes, tooltips, resize and empty/loading states, and testing with no component tree to inspect. The fixed black palette fails the project rule "readable in light and dark on all screen sizes". Imperative SVG in effects also bypasses `motion-reduce:` Tailwind variants and the React reconciler (risk of leaks on unmount, Strict Mode double-invoke in dev).

### A2. Roman Vasnev, Analytics Bento

- Page: https://21st.dev/@romanvasnev/components/analytics-bento (preview bundle: https://cdn.21st.dev/romanvasnev/analytics-bento/default/bundle.1792613985756-20fdc569-e8ad-4502-980f-a20da69c357c.html). MIT. Published 21 Oct 2026.
- Visual pattern: four cards on a 12-column grid (`grid grid-cols-12 gap-4`, cards `col-span-12 lg:col-span-5 / lg:col-span-7`), each `rounded-[28px] border border-border bg-card p-5 text-card-foreground shadow-sm` with a 1s fade/translate entrance (`motion-reduce:transition-none`). Card 1: Revenue count-up number, delta pill, small scrubbable line chart with right-hand axis labels. Card 2: Sessions count-up with mirrored desktop/mobile wave chart (three weeks, faded prior weeks). Card 3: Sales by category with a segmented control (Weekly/Monthly/Yearly, sliding `bg-background` thumb with `ring-border`) that re-flows a treemap, plus a small table. Card 4: Seasonality radar (12 months) with a year segmented control and two stat tiles.
- Dependencies: none beyond React and Tailwind; "SVG only, no chart library". 19 `useEffect` calls, 13 `requestAnimationFrame`, a `ResizeObserver`; a `CountUp` component. Unlike Finance Bento, the reduced-motion preference is held in React state via a `matchMedia` listener, and the segmented control uses `focus-visible:ring-2 focus-visible:ring-ring` and `aria-` attributes (17 in bundle).
- Theme: theme-aware. The bundle defines `:root` and `.dark` shadcn variable sets in oklch, the demo ships a ThemeProvider (`?theme=` query, default light), and the page is `bg-background` with a dot-grid made from `color-mix(in oklab, var(--color-foreground) 7%, transparent)`. Verified in the browser: toggling `html.dark` switched body to `oklch(0.145 0 0)` and cards to `oklch(0.205 0 0)` with legible charts in both modes. Category colours in the demo are fixed hex (`#7CFF5B`, `#8B3DFF`, `#FFB800`, `#FF5A1F`) but are passed in as props, so they can be swapped for `var(--chart-1..5)`.
- Good for: a product dashboard in an existing shadcn app; it inherits the app's radius, border and card tokens.
- Mapping to an exam platform: Revenue card = overall predicted band with 30-day trend line (scrub to see each mock); Sessions card = minutes practised per hour-of-day, Listening vs Reading waves (or this week vs prior weeks); Treemap card = question-type accuracy (True/False/Not Given, Matching Headings, Summary completion, Map labelling...) sized by question count, coloured by skill, with the segmented control switching This week / This month / All time; Radar card = band per skill (L/R/W/S) and per Writing criterion (Task Achievement, Coherence, Lexical Resource, Grammar) with a 2025 vs 2026 style "last mock vs best mock" toggle.
- Trade-offs: same imperative-SVG caveat as A1, but the card shell, tokens and segmented control are reusable as-is. Treat it as a layout and styling reference and re-implement the charts with shadcn/ui charts (Recharts) so series are props and tooltips/legends/axes come for free.

### A3. UI Layouts, Draggable Grid Dashboard ("default-swapy")

- Page: https://21st.dev/@uilayout.contact/components/default-swapy. Registry source: https://ui-layouts.com/r/default-swapy.json. MIT (the demo). Published 23 Sep 2026. Dependencies: `swapy`, `lucide-react`.
- Visual pattern: a 12-column CSS grid (`grid grid-cols-12 gap-2 md:gap-6`) of nine fixed-height (`h-64`) widget cards with responsive spans (`lg:col-span-4 sm:col-span-7 col-span-12` etc.). Each card is wrapped in `SwapySlot` (`data-swapy-slot`) and `SwapyItem` (`data-swapy-item`); dragging one card onto another swaps the two. A small `components/ui/swapy.tsx` wrapper exposes `SwapyLayout` (creates `createSwapy(container, config)` in a `useEffect`, destroys on unmount), `SwapySlot`, `SwapyItem`, `DragHandle`.
- Theme: the demo cards use fixed Tailwind palette classes (`bg-emerald-600`, `text-yellow-200`, `bg-blue-100`, `bg-purple-300`, `bg-pink-200`), not shadcn tokens; only the slot highlight has a `dark:` variant. The shell (`bg-background`) is token-based, the widgets are not.
- Swapy library status (npm registry and GitHub API, checked 26 Oct 2026): `swapy` 1.0.5, last published 19 Jan 2025; GitHub TahaSh/swapy last push 19 Jan 2025, 8.5k stars, 51 open issues, 6 open PRs, not archived. So no release or commit in about 21 months. Framework-agnostic (vanilla DOM); React is supported through `createSwapy` in `useEffect`, and for dynamic lists via `manualSwap: true`, `utils.initSlotItemMap`, `utils.toSlottedItems`, `utils.dynamicSwapy` (docs: https://swapy.tahazsh.com/docs/framework-react-dynamic). The docs do not address React Strict Mode. Licence: GPL-3.0 on npm; the README states a commercial licence must be purchased for proprietary commercial applications (https://swapy.tahazsh.com/license). Keyboard operation and accessibility are not documented. Source: https://registry.npmjs.org/swapy, https://api.github.com/repos/TahaSh/swapy, https://github.com/TahaSh/swapy.
- Implementation notes from the source: the wrapper's effect depends on `[config, onSwap]` and the demo passes inline object/function literals, so Swapy is destroyed and recreated on every render of the parent unless memoised; the demo also uses `initialItems` in a `useMemo` dependency list (module constant, harmless but a lint smell) and only `console.log`s the new slot map rather than persisting it.
- Good for: user-customisable widget boards where people genuinely rearrange things (ops consoles, personal home screens).
- Mapping to an exam platform: a "My dashboard" page where a learner reorders tiles (Next mock, Band trend, Weak question types, Vocabulary review, Writing feedback). Realistically, learners rarely reconfigure dashboards and it adds persistence work (slot map per user) for little learning value.
- Trade-offs: WCAG 2.2 SC 2.5.7 Dragging Movements (AA) requires every drag-based function to also work by single pointer without dragging, e.g. a "move up/down" menu per card (https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html); Swapy gives no such alternative. Combined with the GPL/commercial licence and a stalled release cadence, it is a poor dependency for a proprietary exam product. If reordering is ever needed, `@dnd-kit` (MIT, keyboard sensors built in) or shadcn-compatible sortable patterns are safer.

### A5. Imperative SVG in useEffect vs a React chart library (Recharts)

- What the Vasnev bentos do: build SVG nodes with `document.createElementNS` and mutate attributes in `requestAnimationFrame` loops inside `useEffect`, with a `ResizeObserver` for width. Pros: tiny bundle, pixel-exact art direction, 60fps animations, no library API to learn. Cons for a team that will wire real data: data is not declarative (effects must diff and redraw on every prop change), no tooltip/legend/axis/scale primitives, no empty/loading/error states, no SSR, hard to unit-test, animations ignore `prefers-reduced-motion` unless hand-coded, and every new metric means new drawing code. Two of the bundle's `useEffect`s already re-create nodes on each run.
- What shadcn/ui charts give: copy-paste components on Recharts v3 (shadcn says "We do not wrap Recharts"), `ChartContainer` + `ChartConfig` for labels/colours, `ChartTooltip`/`ChartLegend`, theming via `--chart-1..5` and `var(--color-<key>)` with a `.dark` override, and an `accessibilityLayer` prop that adds keyboard navigation and screen-reader support. https://ui.shadcn.com/docs/components/chart
- Recharts status: v3.10.1 (25 Jul 2026), 3.11 canaries weekly through 24 Oct 2026, MIT, peer deps React 16.8-19. https://registry.npmjs.org/recharts
- Verdict: keep the bento shell, segmented control and card tokens from Analytics Bento; draw the charts with shadcn/ui charts. For a bespoke piece (dot-matrix band number, band gauge) write a small declarative SVG React component (JSX, props in, no DOM mutation), which keeps the art direction without the effect-driven drawing.

## Part B: best-practice research

### B1. Learning and ed-tech dashboard UX: what learners use, progress visualisation, vanity metrics

Findings
- Learners and teachers want different things from the same data. A Utrecht thesis on learning analytics dashboards (LADs) reports that the way students want to track progress is "fundamentally different" from how teachers monitor it; design the learner view for self-regulation, not admin reporting. https://studenttheses.uu.nl/handle/20.500.12932/45437
- The reference frame matters more than the chart. De Vreugd et al. (2023, Studies in Educational Evaluation 79) found learners use the dashboard's reference frame almost to the exclusion of other external comparators, and a peer reference frame produced the most internal feedback. https://research-portal.uu.nl/en/publications/the-role-of-reference-frames-in-learners-internal-feedback-genera/ A 2024 experiment (Gallagher et al., 42 trainees) found progress-framed dashboards did not raise self-efficacy more than social-framed ones; the progress frame led to less time reviewing the dashboard but more time on detailed task feedback. https://researchinformation.umcutrecht.nl/en/publications/reference-frames-for-learning-analytics-dashboards-the-progress-a/ For an IELTS simulator this argues for two frames side by side: "you vs your target band" (progress/mastery) and an opt-in "you vs other learners aiming for 7.0" (peer).
- Dashboards without interpretation add load. A 2025 randomised trial with 8,745 MOOC learners (preprint) found a LAD only changed behaviour when it carried feedback; dashboards without interpretive support "may add cognitive burden" and had no effect on final grades. https://www.preprints.org/manuscript/202509.1836/v1 Every tile should answer "so what, and what next" (e.g. "Matching Headings: 48%. Do the 10-minute drill").
- Show distance to the goal, not just what is done. Open edX's Visual Course Progress proposal (FC-0071) exists because learners could not see "how far to pass"; its goals are progress towards the passing threshold and letting learners choose the visual that fits their goal. https://openedx.atlassian.net/wiki/x/DYBkEgE For IELTS: show band gap to target per skill, not "lessons completed".
- The EUNIS 2018 Learning Scorecard paper frames the core problem as choosing "meaningful and unambiguous learning indicators", and reports that right-time performance data plus peer benchmarking increased engagement. https://repositorio.iscte-iul.pt/bitstream/10071/19776/1/EUNIS_2018_paper_80-Learning%20Scorecard%20Dashboards-%20visualizing%20student%20learning%20experience.pdf
- Streaks and vanity metrics. Khan Academy retired streaks on 4 Jan 2021 because over 99% of learners did not use them regularly and "streaks can actually be demotivating" when circumstances outside a learner's control break them; its current dashboard leads with a Mastery Learning card (Familiar/Proficient/Mastered) and separates activity counts. https://support.khanacademy.org/hc/en-us/community/posts/360075847492 and https://support.khanacademy.org/hc/en-us/articles/46935588089997-How-do-I-use-the-student-dashboard-in-Khan-Academy Growth.Design's Duolingo retention case study names the Zeigarnik effect, investment/sunk cost and triggers behind streaks, but also records that losing a streak is a major reason people quit, that the rainbow of colours competes with the primary action, and warns against confirm-shaming copy. https://growth.design/case-studies/duolingo-user-retention Smashing Magazine (Ayomipo, Feb 2026) lists the design rules if a streak is used at all: tiny daily action, grace mechanisms (freeze, decay instead of reset), celebrate milestones, never guilt-based copy. https://www.smashingmagazine.com/2026/02/designing-streak-system-ux-psychology/ UX Collective's "Gamification gone wrong: stop the streaks" makes the vanity-metric argument directly. https://uxdesign.cc/gamification-gone-wrong-stop-the-streaks-c3de42618ae
- General dashboard rules that apply: define the dashboard's purpose first (operational vs analytical), the inverted pyramid (headline numbers, then trends, then detail), pick chart type by the question (FT Visual Vocabulary), limit widgets per view. Bakusevych, "10 rules for better dashboard design" https://uxplanet.org/10-rules-for-better-dashboard-design-ef68189d734c; Smashing Magazine data-visualisation roundups https://www.smashingmagazine.com/the-smashing-newsletter/smashing-newsletter-issue-462 ; Bach et al., "Dashboard Design Patterns" (IEEE VIS 2022, 144 dashboards; eight pattern groups; "Stratified" layout = high-level on top, detail below) https://arxiv.org/abs/2205.00757 and https://dashboarddesignpatterns.github.io/patterns.html

Metrics learners actually act on (synthesis for the IELTS simulator)
- Primary: predicted overall band and per-skill band (L/R/W/S) against the target band, with the gap in half-bands.
- Diagnostic: accuracy by question type (Reading: TFNG, matching headings, summary completion...; Listening: form completion, map labelling, multiple choice), time per question vs the exam budget (Reading: ~20 min per passage; 60 min total for 40 questions), unanswered/guessed counts.
- Writing: band per criterion (Task Achievement/Response, Coherence and Cohesion, Lexical Resource, Grammatical Range and Accuracy) and word count vs minimum (150/250).
- Next action: one recommended drill and the next scheduled full mock.
- Avoid as headline metrics: streaks, total minutes, logins, "lessons completed" counts, badges. Keep them, if at all, as secondary, non-loss-framed context.

### B2. Bento grid dashboards: when they help and when they hurt

- Fit: bento suits content with a natural hierarchy (a few things matter more than the rest); if items are equally weighted use a plain grid or list. Poor fits: text-heavy pages, data tables, long forms, anything where reading order matters. Use at most 1-2 hero tiles per viewport ("when everything is big, nothing is important"), uniform 16-24px gaps, no more than 2-3 accent colours in a dashboard. Meyer, StudioMeyer (Nov 2025, updated Sep 2026) https://studiomeyer.io/en/blog/bento-grid-layouts
- Density and scanning: size, not position, signals importance; each tile is a bounded chunk (headline 1-6 words, 1-2 lines of body); desktop 3-4 columns, tablet 2, mobile 1 with cards reordered by priority rather than desktop position; a stacked bento on mobile is just a list, so vary heights and keep internal card design. SaaSFrame, "Designing Bento Grids That Actually Work" (2026) https://www.saasframe.io/blog/designing-bento-grids-that-actually-work-a-2026-practical-guide (ignore its unsourced 47%/38% statistics). freeCodeCamp overview https://www.freecodecamp.org/news/bento-grids-in-web-design/
- Accessibility and reading order: CSS grid placement, `grid-auto-flow: dense` and `order` change the visual order but not the DOM order, so tab order and screen-reader order can become disjointed. Write the DOM in reading order and use spans for layout; verify with a tab-stops checker. Rachel Andrew, "Grid, content re-ordering and accessibility" (2019) https://rachelandrew.co.uk/archives/2019/06/04/grid-content-re-ordering-and-accessibility ; WCAG 2.4.3 Focus Order https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html ; Bach et al. trade-offs (screen space vs pages vs abstraction vs interactivity) https://dashboarddesignpatterns.github.io/tradeoffs.html
- Verdict for the exam platform: bento for the overview page only (one hero band tile, 3-5 supporting tiles, stratified top-down), never for the exam shell, results tables or feedback reading. Collapse to a single prioritised column under 768px.

### B3. Light vs dark theme for a reading-heavy exam app

- Research: NN/g (Budiu, Feb 2020) reviews Piepenbrock et al. 2013 (Ergonomics; Human Factors): positive polarity (dark text on light) won on visual acuity and proofreading for younger and older adults, the advantage grew as type got smaller, and participants could not perceive the difference themselves, so do not rely on preference surveys. Fatigue did not differ. Dark mode helps some users with cloudy ocular media (cataract) and is preferred by about a third of mobile users. NN/g's recommendation: do not default to dark for the general population, but offer a switch, follow the OS setting, and make long-form reading apps support dark across every screen. https://www.nngroup.com/articles/dark-mode/ Secondary coverage with Budiu quotes: https://habr.com/ru/amp/publications/473962 and https://hardware.slashdot.org/story/20/02/16/2041240/dark-mode-vs-light-mode-which-is-better
- Astigmatism and halation: light text on black makes the iris open and blurs focus for astigmatic readers (widely repeated UBC/Sensory Perception Lab explanation; no primary paper found). https://raghuveerdotnet.netlify.com/posts/darkmode ; a11y-focused summary https://a11ywithdiana.substack.com/p/and ; Walter, "Dark mode and accessibility myth debunked": offer both, let the user choose, and check contrast separately in each mode. https://stephaniewalter.design/blog/dark-mode-accessibility-myth-debunked/
- Exam convention: the official computer-delivered IELTS demo (Inspera player at demo-ielts.inspera.com, observed 26 Oct 2026) is a white shell: black text, left passage / right questions, a Notes panel on the right, Part tabs and a numbered question navigator along the bottom, the timer top-centre. IDP documents the interface: stopwatch "in the upper middle part of the screen" that flashes at 10 and 5 minutes, navigation bar at the bottom for all 40 questions, Review button, highlight and notes, a Settings control for font size and background colour (e.g. yellow on black as an opt-in accommodation). https://ielts.idp.com/prepare/article-how-computer-delivered-ielts-works and https://takeielts.britishcouncil.org/take-ielts/book/ielts-on-computer TOEFL iBT and PTE Academic similarly ship a timer, Review screen and light interface. https://www.kaptest.com/study/toefl/whats-tested-on-the-toefl-reading-section/ ; https://www.pearsonpte.com/teachers/webinars-2026/2026/03/navigating-pte-academic--a-practical-guide-to-the-test-interface/
- Recommendation: exam shell defaults to light with a strict neutral palette that matches the real test (fidelity is the product's point); expose the same colour-scheme accommodations the real test has (font size, high-contrast and yellow-on-black) as explicit settings; dashboard and marketing pages follow the OS `prefers-color-scheme` with a manual override, and contrast is checked to WCAG AA in both modes.

### B4. Design-system choice for React + Tailwind + shadcn

- shadcn/ui charts: copy-paste components over Recharts v3 (not a wrapper), `ChartContainer` with `ChartConfig` (label, icon, colour or `{light, dark}` theme), `ChartTooltip`/`ChartLegend`, colours via `--chart-1..5` and `var(--color-<key>)` with `.dark` overrides, `accessibilityLayer` for keyboard and screen-reader access. Upgrading from v2: use `var(--chart-1)` not `hsl(var(--chart-1))`. https://ui.shadcn.com/docs/components/chart Recharts: 3.10.1 (Jul 2026), MIT, React 16.8-19, active canaries. https://registry.npmjs.org/recharts
- Tremor: Vercel acquired Tremor on 22 Jan 2025; Tremor Blocks went free and MIT and the founders joined Vercel design engineering (Vercel dashboard and v0). https://vercel.com/blog/vercel-acquires-tremor The `@tremor/react` npm package is still 3.18.7 (13 Jan 2025) with React 18 peer deps and Recharts bundled as a dependency; no release since. https://registry.npmjs.org/@tremor/react Tremor Raw (copy-paste, Tailwind v4-friendly) lives on at tremor.so as per-file snippets built on Recharts. https://www.tremor.so/docs/getting-started/installation/next Use Tremor Raw blocks as layout inspiration (KPI card, bar list, tracker, progress circle) but implement with shadcn/ui charts to keep one token system. Comparison context: https://www.pkgpulse.com/guides/recharts-v3-vs-tremor-vs-nivo-react-charting-2026
- "Exam mode" layout that strips chrome: NN/g on zen/focus mode (Fessenden, 2016) warns that hiding tools raises recall load and interaction cost, so keep the few essential controls visible (timer, question navigator, review flag, help, exit) and hide everything else (app nav, sidebar, notifications, theme toggle). https://www.nngroup.com/articles/zen-mode/ The Australian Agriculture Design System's focus-mode pattern: system-controlled (not a user toggle) for multi-page flows, warn on leave, always provide a clear way out. https://design-system.agriculture.gov.au/patterns/focus-mode Derivita and EdisonOS document that full-screen "focus mode" is a distraction reducer, not a secure lockdown. https://support.derivita.com/focus-mode Implementation: a separate `ExamLayout` route group (no AppShell), `<main>` with the two-pane passage/questions split, sticky top bar (Part, timer, Settings), sticky bottom navigator with `scroll-padding` so focused answers are never hidden (WCAG 2.4.11), `beforeunload` guard, and a `data-theme="light"` lock on the exam route.
- Type pairings: Geist Sans (Vercel, OFL 1.1, 9 weights, "readability, precision, restrained Swiss style", built for interfaces and body copy) or Inter for UI and dashboards; Geist Mono for timers, band numbers and tabular figures (`font-variant-numeric: tabular-nums`). https://vercel.com/font For passages: Literata (TypeTogether, commissioned by Google for Play Books, OFL, darker regular weight and generous spacing tuned for backlit screens, optical-size and weight axes in Literata 3) https://www.typetogether.com/literata-font or Source Serif 4 (Adobe, OFL, optical sizes Caption/Text/Subhead/Display, variable) https://github.com/adobe-fonts/source-serif. Evidence on serif vs sans is mixed: a 2026 study with 132 adults (Verdana vs Times, screen vs paper) found font type did not interact with medium and familiarity mattered more https://www.leibniz-ipn.de/en/research/publications/just-the-font-types-effects-of-serif-vs-sans-serif-font-types-on-text-comprehension-in-screen-vs-paper-reading ; older small studies favour Verdana/Georgia for long on-screen text https://doi.org/10.5539/ies.v6n3p26. So the choice is less about serif per se and more about a face designed for continuous reading at 16-18px with a tall x-height, open apertures, clear 1/l/I and distinct italics, plus 60-75 characters per line and 1.5-1.6 line height. The real IELTS interface uses a plain sans (Inspera default), so a legible sans (Geist/Inter at 17px) is the fidelity choice for the exam shell; a reading serif (Literata/Source Serif 4) fits the practice/review mode where comfort matters more than fidelity. Offer the font-size control the real test offers.

### B5. Accessibility requirements for timed tests

- WCAG 2.2 SC 2.2.1 Timing Adjustable (A): for each time limit, allow turn off, adjust (at least 10x) or extend (warn, 20 s to extend, at least 10 times), unless the limit is part of a real-time event, is essential ("extending it would invalidate the activity"), or exceeds 20 hours. The Understanding text explicitly allows a third party to control limits where user control would invalidate the outcome, "for example granting double time on a test". https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html Practice: strict timer by default (essential, matches the real test), plus an accommodations setting (x1.25, x1.5, x2, untimed) chosen before the mock starts and recorded on the result, warnings at 10 and 5 minutes (as the real test does), and an explicit "end section" confirmation.
- SC 2.2.6 Timeouts (AAA): warn about inactivity timeouts that lose data, or keep data for 20 hours. Autosave answers continuously and say so once at the start. https://www.w3.org/WAI/WCAG22/Understanding/timeouts.html
- SC 2.4.3 Focus Order (A): focus must follow a meaningful order; dialogs (e.g. "Submit section?") take focus and return it; CSS-reordered grids must be checked. https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html
- SC 2.4.11 Focus Not Obscured (Minimum) (AA, new in 2.2): sticky headers, footers and side panels (a question navigator or notes panel) must not completely hide the focused control; use `scroll-padding` (technique C43) or make panels displace rather than overlap content. https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html SC 2.4.7 Focus Visible (AA): visible focus ring on every answer control and navigator button. https://www.w3.org/WAI/standards-guidelines/act/rules/oj04fd/
- Keyboard access to the navigator: the question navigator is a toolbar/tablist of 40 buttons: arrow keys move, Enter/Space jump, `aria-current="true"` for the current question, `aria-pressed` or an "Answered/Flagged" text label (not colour alone) for state; Previous/Next buttons reachable in tab order; a skip link from the passage to the questions; the highlight/notes tools must have keyboard equivalents.
- SC 2.5.7 Dragging Movements (AA): any drag interaction (drag-to-swap widgets, drag answers into gaps for matching questions) needs a single-pointer alternative such as select-then-click or a move menu. https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html
- SC 2.3.3 Animation from Interactions (AAA) and reduced motion: honour `prefers-reduced-motion` (technique C39) for count-ups, chart entrances and the flashing timer (use a colour change plus text instead of flashing). https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html Also keep SC 2.3.1 Three Flashes in mind for the timer warning.
- Reading accommodations present in the real test and expected here: font-size control, screen-colour options (including yellow-on-black), zoom to 200% without loss (SC 1.4.4/1.4.10), 4.5:1 text contrast in every theme (SC 1.4.3).

## Verdict: which reference suits the IELTS Academic simulator

Use a combination, with Analytics Bento as the primary dashboard reference:

1. Analytics Bento (A2) for the learner overview page. It is the only one of the four that is theme-aware through shadcn tokens, keeps a 12-column responsive bento with a stratified layout, and its segmented control and `rounded-[28px] bg-card` shell drop straight into a shadcn app. Re-implement its charts with shadcn/ui charts on Recharts so the team can bind real data, get tooltips, legends, `accessibilityLayer` and dark-mode colours from `--chart-1..5` for free. Keep the one bespoke piece worth keeping (a dot-matrix or count-up band number) as a small declarative SVG component rather than DOM mutation in effects.
2. Content Block (A4) for the public site and onboarding pages (how the simulator works, what you get). Not for live data.
3. Finance Bento (A1) only as art-direction inspiration (gradient hero, lime accent, Geist Mono numerals). Its fixed black palette and imperative SVG make it unfit as a base for a light-default, reading-heavy product that must pass WCAG AA in both themes.
4. Draggable Grid / swapy (A3): do not adopt. GPL-3.0 with a paid commercial licence, no release or commit since January 2025, no keyboard or single-pointer alternative (WCAG 2.2 SC 2.5.7), fixed Tailwind colours in the demo, and user-rearrangeable widgets add persistence work without learning value. If reordering is ever required, use `@dnd-kit` (MIT, keyboard sensors).

The exam shell is a separate design from all four: a light, chrome-free `ExamLayout` modelled on the official Inspera-based IELTS on computer interface (passage left, questions right, timer top-centre, Part tabs and numbered navigator bottom, Notes panel, Settings for font size and screen colours), with Geist/Inter at 17px for fidelity, strict timer by default with pre-selected accommodations (x1.25 to untimed) per WCAG 2.2.1's third-party-control allowance, autosave, `scroll-padding` for the sticky navigator, and `prefers-reduced-motion` honoured for the timer warning.
